# Admin Control Center: plan and decisions

## What already existed (reused, not duplicated)

- **Administration → Infrastructure.** Six pages: health, PostgreSQL, ClickHouse, event pipeline, migrations, configuration (`src/pages/admin/InfrastructureAdmin.tsx`, `server/src/routes/infrastructure.ts`). They show real diagnostics and stay as the detailed views. The new Control Center links to them and reuses `getMigrationStatus`, `testPostgres` and `testClickHouse`.
- **Settings → Integrations.** Per-organization Google connections. This is tenant scope and was left unchanged; the admin registry only reports the number of connections by status.
- **Platform-admin guard.** `requirePlatformAdmin` and `PLATFORM_ADMIN_USER_IDS`, reused.
- **Credential encryption.** `server/src/integrations/crypto.ts` (AES-256-GCM, versioned key ring), reused.

## What was added

| Area | Frontend | API (`/api/v1/admin`, platform admins only) |
| --- | --- | --- |
| Overview and diagnostics | `/admin/control-center` | `GET /diagnostics`, `GET /diagnostics/export`, `POST /diagnostics/jobs/:kind/:id/retry` |
| Integrations and API keys | `/admin/integrations` | `GET /integrations`, `PUT /integrations/:provider/credential`, `POST /integrations/:provider/test`, `POST /integrations/:provider/enable` and `/disable`, `DELETE /integrations/:provider/credential`, `POST /integrations/encryption/reencrypt` |
| Users and access | `/admin/users` | `GET /users`, `GET /users/:id`, `POST /users/:id/activate` and `/deactivate`, `POST /users/:id/revoke-sessions`, `PATCH /users/:id/memberships/:orgId`, `POST /users/:id/password-reset`, `GET` and `POST /account-credentials` |
| Audit | Shown in the Control Center | `GET /audit` |
| Password reset (public) | `/reset-password` | `POST /api/v1/auth/password-reset/request`, `POST /api/v1/auth/password-reset/confirm` |

The **Administration** navigation group is shown only when `GET /auth/me` returns `isPlatformAdmin: true`. Hiding it is cosmetic: every admin endpoint checks the token, `PLATFORM_ADMIN_USER_IDS` and `users.active` itself.

## Decisions

1. **Scope of credentials.** The only provider credential the product consumes globally is the AI key (OpenRouter). It is platform-wide, so only platform administrators manage it. Organization owners and admins cannot change it. No per-organization provider keys were introduced, because the tenancy model does not require them. Google Search Console stays per-organization through OAuth.
2. **No meaningless settings.**
   - Email, licensed SEO data and payments have no code path, so no key form exists for them. Email and licensed data are listed as "Not available" with the reason.
   - Deployment-level secrets (database, JWT, cookie, encryption keys, Google OAuth client, ClickHouse) are shown by name and presence, with a test where one exists. They are never editable in the UI, because the application cannot change its host's environment.
3. **Validation before storage.** A submitted key is checked with the provider's cheapest non-destructive endpoint (`GET https://openrouter.ai/api/v1/key`: no model call, no cost). It is stored only if the provider accepts it. Any other outcome leaves the previous key untouched.
4. **Activation.** A stored, verified key takes effect at once in the process that saved it. Other processes pick it up within 60 seconds (`maybeRefreshPlatformCredentials`). Stored keys are re-validated at startup and every 6 hours. Only a provider rejection (`invalid`, `permission_denied`) stops a key being used. Outages, timeouts and quota exhaustion never erase or disable it.
5. **Precedence.**
   - An enabled, non-rejected stored key is used first.
   - A stored key that an admin **disabled** turns the integration off.
   - Otherwise the deployment variable (`OPENROUTER_API_KEY`) applies, as before this phase.
6. **Generated credentials.** External provider keys are never generated by the application. The only generated secrets are:
   - the one-time password of the designated account (`ADMIN_CREDENTIAL_ACCOUNT_EMAIL`, default `info@zigmaneural.com`), from `crypto.randomInt`, about 120 bits, stored only as a bcrypt hash;
   - password-reset tokens: 32 random bytes, stored as a SHA-256 hash.
7. **No dangerous tools.** There is no SQL console, shell, URL fetch or arbitrary command execution. Job retry is limited to two job types where retrying cannot duplicate work.

## Not done (and why)

- **Email delivery.** There is no provider. Admin-initiated password-reset links therefore return `503 EMAIL_NOT_CONFIGURED`, and no token is created. Adding a provider means implementing `server/src/platform/mailer.ts`, which needs owner approval and credentials.
- **Internal API tokens** (machine credentials for the platform API). No existing feature consumes them, so none were added; adding unused tokens would be meaningless attack surface. When one is needed: random 32 bytes, store only the SHA-256, add scopes, expiry and revocation, and show the token once.
- **Persistent error log.** Server errors are kept in a 100-entry in-memory buffer per process, with route pattern and request id only. Stack traces, URLs and personal data are not stored. A durable error store or APM service needs an owner decision.
- **Feature flags beyond integrations.** There is no flag mechanism, and none was invented. Features switch on and off with their integrations (`capabilityAvailable`).
