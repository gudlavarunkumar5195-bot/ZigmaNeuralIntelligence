# Frontend audit: ZigmaNeuralIntelligence

All findings come from reading code. Nothing was modified or run, including `tsc` and the tests. I did not open `.env` files. `utils/supabase/info.tsx` exports two constants and I did not print them. `server.env.example` exists. Line numbers are approximate for the one-line page files.

## 0. Architecture facts

- **Stack:** React 19, `react-router` 8 with `createHashRouter`, Tailwind 4, recharts.
- **State and hooks:** There is no store, no custom hooks directory and no query library. Every page uses local `useState` and `useEffect`.
- **Deploy:** `app.yaml` serves the frontend and API from one Fastify process. `VITE_API_BASE_URL=/api/v1` and `VITE_APP_MODE=production` are build-time values.
- **Mode switch:** `src/config/env.ts` defaults `VITE_APP_MODE` to `production`. Any other value means demo mode, in which every API call throws `IntegrationRequired`. No mock data exists in the UI.
- **Supabase edge function:** `supabase/functions/server/index.tsx` is a Figma-Make boilerplate Hono app.
  - It serves only `GET /make-server-3e62fbda/health` and sets `cors origin:"*"`.
  - `kv_store.tsx` is also unused.
  - Nothing in `src` imports it, and `app.yaml` never deploys it.
  - It is dead code. The `*` CORS is harmless only while it stays undeployed.
- **`utils/supabase/info.tsx`:** not imported by `src`.
- **Dead exports:** `src/lib/scoring.ts` and `src/types/index.ts` are never imported by the UI. `scoring.ts` is exercised only by its own test.
- **Dead functions:** `assertProductionConfig()` is never called, so production misconfiguration is never reported at startup. `DemoBanner` is a stub that returns null.

## 3. Findings

**P1**
1. **MonitoringPage is broken.** `MonitoringPage.tsx` returns a read-only card list at about lines 80-120. A second full `return (...)` follows with the create form, Run, Pause, Resume, Disable and "Change frequency" buttons. That second return is unreachable. Users cannot create or manage monitoring. The `action`/`busy` helpers are dead as written.
2. **Settings pages show fabricated "live" data.**
   - Workspace shows "ZigmaNeural Intelligence / Growth / US East + EU West".
   - Team shows "12 active / 2 pending" and the members "Ava Thompson / Miles Chen / Nina Patel", each with a dead "Manage" button.
   - Security shows "MFA Enabled", "Retained 365 days", "SSRF protections Active" and "Rate limiting Enabled".
   - Integrations shows "Supabase Configured" and "CI/CD Enabled".
   - API shows "/api/v1", "200/min" and editable inputs that do nothing.
   - None of this is wired to a backend. The security statements are unverified claims, and `src/tests/production-data.test.ts` does not cover them.
3. **Roughly 17 of 37 routes are placeholders or "integration required".** The affected sections are all of Intelligence, Testing, Infrastructure and Client Reports, plus Control Center and Benchmarks. The backend `/scans/:id/findings`, `/report` and `/evidence` endpoints could back several of them, but the frontend does not call them.

**P2**
4. **Possible syntax errors in `api.ts`, MonitoringPage and AlertsPage.** Type members are separated by a space only: `{ code?: string message?: string }` (`api.ts:195`) and `{ code: string message: string }` (`MonitoringPage.tsx`, `AlertsPage.tsx`). Other cases are `ruleType: string threshold?:` and `{ type: string payload: unknown }`. Strict TypeScript rejects this, though esbuild/oxc may be lenient. I did not run `tsc`, so please confirm `tsc --noEmit` passes. Also check whether `dist/` was built from this source.
5. **401 handling logs the user out on any retry failure.** After a successful refresh, if the retried request returns any non-OK status such as 403 or 500, the code falls through to `clearToken()` and redirects to `/login` (`api.ts:178-191`).
6. **Concurrent 401s each call refresh.** There is no single-flight lock, so with refresh-token rotation, parallel refreshes can invalidate each other. `setToken` also resets the active org to the first one in the JWT, discarding any prior selection.
7. **Token storage.** The access token lives in `sessionStorage` under `zn_token` and in a module variable, so any XSS can read it. Per the code comments, the refresh token is an HttpOnly cookie. There is no localStorage use and no expiry check, since `isAuthenticated()` only checks that a token exists. Refresh happens only reactively on a 401.
8. **Swallowed errors.**
   - Shell.tsx:282 swallows the website-list fetch error.
   - AgentRegistry: `loadDetail` and `handleToggle` (an enable/disable failure gives no feedback).
   - ModelRouter policy tab `.catch(() => {})`.
   - SSE JSON parse `catch {}` in `api.ts`.
   - `apiLogout` `.catch(() => {})`.
   - `res.json()` error parse `catch {}`.
   - There are no `console.log` calls. Only `console.error` appears in `env.ts`.
9. **No role-based UI gating anywhere.** Admin-only actions are shown to all users: QA verify, agent enable/disable, model catalog refresh, and the router and simulators. The backend enforces roles. Users will see raw 403 errors.
10. **The website selector and pages are inconsistent.** The top-bar selector affects only Overview. MyWebsites, ReportsPage and ScanHistory call `apiGetDashboard()` with no `websiteId`, so they ignore the selection.
11. **ScanProgress uses polling and has no cancel.** `subscribeToScanProgress` and `apiCancelScan` are implemented but have no UI. The poll timer keeps running while an error is displayed.

**P3**
12. `app.yaml` hardcodes the QA test email `zigma.qa.20260903@example.com` in `QA_AUTHORIZED_EMAILS`. The bypass flags are `"false"`, but the email is committed.
13. The root `prebuild` script runs `pnpm install --no-frozen-lockfile` for both the root and the server. This causes non-reproducible builds, and installing at build time is a supply-chain concern.
14. `@anthropic-ai/claude-agent-sdk` is listed as a root frontend dependency but is not imported in `src`. It could bloat the install, and it is risky if it ever got bundled.
15. The catch-all `*` route renders a "Construction" placeholder instead of a 404.
16. The marketing numbers on the Login page are hardcoded. Some files have unused imports and variables, such as `location`/`navigate` in Sidebar.
17. A one-line `qa_bypass` option is exposed in the UI for all users, with a note that the server enforces it.
18. Mixed code style: some pages are dense one-liners and others are formatted.

## Headline

The AI stack does not work end to end on a fresh deployment. No code path moves a model out of `DISCOVERED`, so the eligible-model pool is empty and every real agent run fails with `MODEL_FAILURE`.

There are no endpoints that run a model on demand. The only real LLM path is the scan pipeline, called from `services/scan.service.ts:543`.

## Findings

### F-01 (P0) No code path makes any model eligible, so the real path always fails
- **Evidence:** `ai/catalog.service.ts:281` inserts new models as `status='DISCOVERED'`. `ai/registry.service.ts:calculateEligibility` maps `DISCOVERED` to `PENDING_REVIEW`. `getEligibleModels` keeps only `ELIGIBLE`. `enableModel` sets `enabled=TRUE` and recomputes eligibility, but leaves the status as `DISCOVERED`. No migration seeds models, and I found no `AVAILABLE` or `ELIGIBLE` status writes outside the migration enum definitions.
- **Effect:** `filterCandidates` returns no candidates, routing returns `NO_CANDIDATES`, and the orchestrator throws `MODEL_FAILURE` at `orchestrator.ts:129`. Every specialist fails and every scan ends with intelligence status `FAILED`. The only workaround is a manual DB edit.
- **Missing:** an approve or promote workflow, or a rule for `DISCOVERED` to `AVAILABLE`, plus a seeded or approved baseline model.
- **Recommendation:** add an admin "approve model" endpoint that sets the status and audits it, or auto-promote under policy. Add a startup health check that warns when the eligible set is empty.
- **Tests required:** a catalog refresh, approval and eligibility integration test. A routing test against a real DB fixture, not a mock.

### F-02 (P1) A tenant admin's routing-policy update deactivates the global policy
- **Evidence:** `router/routing-policy.ts:122-130`. `getActivePolicy(orgId)` falls back to the global row (`org_id IS NULL`) when the org has no policy. `updateActivePolicy` then runs `UPDATE routing_policies SET is_active=FALSE WHERE id=$1` on that global row, before inserting an org-specific row. The deactivate and insert are also not in a transaction.
- **Effect:** the first policy change by any org owner or admin disables the platform default for every tenant that has no policy of its own. A crash between the two statements leaves the org with no active policy.
- **Recommendation:** only deactivate when `current.orgId === orgId`, and run the change inside `withTransaction`. Add a unique partial index on `(org_id) WHERE is_active`.
- **Tests required:** two-tenant policy update test. A transaction rollback test.

### F-03 (P1) Global AI resources are controlled by any tenant admin
- **Evidence:** `routes/models.ts:249` (catalog refresh), `:285` and `:295` (enable/disable model), `routes/agents.ts:110` and `:121` (enable/disable agent). All use the per-org `requireRole("owner","admin")`. The target tables (`models`, `specialist_agents`) have no `org_id`.
- **Effect:** one tenant's admin can disable a model or a specialist agent for every tenant and break all scans. A tenant admin can also trigger paid-key catalog fetches repeatedly.
- **Recommendation:** add a platform-operator role, or make enablement per-tenant (`org_model_overrides`). Rate-limit and single-flight the catalog refresh.
- **Tests required:** route tests showing a non-platform admin gets 403, and cross-tenant effect tests.

### F-04 (P1) The quality gate does not verify quality
- **Evidence:** `ai/quality/evaluator.ts:6-12` and `scan-pipeline.ts:100,124`.
  - Grounding scores 100 whenever `findingEvidence.length >= findings.length`, and 100 when there are no findings.
  - `FINDING_QUALITY`, `CONSISTENCY` and `EVIDENCE_COMPLETENESS` are not computed from content. `CONSISTENCY` and `FINDING_QUALITY` are not set at all and contribute 0 to the weighted sum, but coverage defaults to 100 when no scope is supplied.
  - Callers pass `evidenceValid` as "every finding has at least one evidence id". The evidence has no semantic relationship to the finding. `validateGrounding` is never called, so tenant, task, resource and freshness are never checked.
  - `requiredCoverage`, `evidenceFresh`, `instructionValid`, `securityViolation` and `unauthorizedTool` are never supplied by any real caller, so those branches never fire.
- **Effect:** a result with zero findings scores 100 and is ACCEPT. Any model-fabricated finding that cites one real evidence id is ACCEPT. The gate is an "evidence ids non-empty" check labelled as a quality score.
- **Recommendation:**
  - Call `validateGrounding` with the resolved evidence records.
  - Compute coverage from discovered pages versus the pages cited.
  - Decide explicitly what an empty result means for each agent.
  - Pass the policy-gate and instruction-validation outcomes into the evaluator.
- **Tests required:** negative tests (evidence from another resource, stale evidence, an empty result for an agent that should find something). A pipeline test that asserts a rejected result is not persisted.

### F-05 (P1) Unbounded cost and time per scan, with a 2-minute stage lease
- **Evidence:** `ox-alpha.ts:68-69` loops over `1 + fallbacks` models times `maxRetries`, with `maxRetries` defaulting to 3 and the config value uncapped. The orchestrator passes `routing.fallbackModels` (up to 3). Timeout is up to 60s per attempt, and `policy-gate.ts` checks timeout but never `maxRetries`. The routing call adds its own retry loop. Six specialists run in parallel (`Promise.all`) plus one synthesis call. `scan-pipeline.ts:166` sets the stage claim lease to 2 minutes with no heartbeat.
- **Effect:**
  - The worst case is about 4 models × 3 attempts × 60s, plus backoff, per agent. That is roughly 12 calls per agent and 80+ per scan, plus the routing calls.
  - A stage can exceed its lease, so another worker can re-claim it. That duplicates paid executions and conflicts on findings.
  - There is no per-org or per-scan token or cost budget and no concurrency cap.
- **Recommendation:** cap `maxRetries` and total attempts in the policy gate and in `OxAlphaExecutor`. Add a per-scan deadline passed through to the executor. Add a lease heartbeat or a lease longer than the worst case. Enforce a per-org daily token budget from `agent_executions` usage.
- **Tests required:** a test that the worst-case attempt count is bounded, a lease-expiry test, and a budget-exceeded test.

### F-06 (P2) Timeout handling is mis-wired
- **Evidence:** `openrouter.ts:128` converts an `AbortError` into `ProviderError("CANCELLED", …, retryable=false)`. `ox-alpha.ts:109` looks for `err.name === "AbortError"`, which never matches a real provider failure. The `TIMEOUT` code is never produced.
- **Effect:** a timeout is classified `CANCELLED` and non-retryable. It breaks to the next fallback model and never retries the same model. The timeout test passes only because its mock throws a raw `AbortError`, so it doesn't reflect the real provider. Reliability stats can't tell a timeout from a user cancel. There is no overall wall-clock limit across attempts.
- **Recommendation:** have the executor detect its own timeout (`controller.signal.aborted`) and map it to `TIMEOUT`. Decide the retry policy explicitly.
- **Tests required:** use the real `OpenRouterProvider` with a stalled mocked fetch, and assert the error code and behaviour.

### F-07 (P1) Prompt-injection exposure through "trusted" context
- **Evidence:** `orchestrator.ts:253-259` prints every context key except `websiteContent`, `rawHtml` and `userInput` under the heading "Structured context (system-provided, trusted)". `scan-pipeline.ts:90` puts `discoveryPages` there. Those pages carry attacker-controlled data: title, meta description, headings, image alt text, link URLs, structured data and response headers, as well as `deterministicEvidence` content. The pipeline never sets `websiteContent`, so the untrusted label and the 8000-char slice are never applied.
- **Effect:** a crawled site can place instruction text in a `<title>` or JSON-LD, and the model sees it labelled as trusted. Mitigations that do exist: the system prompt's "treat as untrusted" policy line, a strict JSON output contract, evidence-id allowlisting, and persistence only after quality and schema checks. A page can still push false findings, severities and recommendations that cite real ids. There is also no total size cap on the context, so a large crawl can exceed the context window or inflate cost.
- **Recommendation:** label `discoveryPages` and scanner evidence as untrusted data. Wrap them in delimiters and cap their size. Strip control strings. Never describe model-visible site data as trusted.
- **Tests required:** an injection fixture through title and JSON-LD that asserts the prompt labels it untrusted, and a size-cap test.

### F-08 (P2) Configuration that exists but has no effect
- `routing_policies.max_attempts` and `require_cross_model_verification` are stored and exposed via the API but never read.
- `model_preferences` (`PUT /models/preferences/:orgId`) is never consumed by routing.
- `getModel` and `model_benchmarks` have no writer. `recordReliabilityEvent` has no caller. Consequently reliability and historical scores are always UNKNOWN, and the scorer falls back to a neutral 50.
- Impact: admins believe controls are applied when they are not.
- Tests required: tests that assert each control changes the routing output, or remove the controls.

### F-09 (P2) Regeneration, adaptation and the retry loop are not wired in
- **Evidence:** `planRegeneration` is called only from its simulate route, and `planAdaptation` has no caller. The pipeline throws `QC_REJECTED` and fails the stage on any non-ACCEPT result (`scan-pipeline.ts:101`). No `regeneration_runs` or adaptation rows are ever written.
- **Effect:** the "adaptive" layers are simulation-only. The advertised improvement loop (collect more evidence, retry with new instructions or a different model) doesn't exist. A single quality miss fails the specialist.
- **Tests required:** if wired in, a bounded-loop test (`maxIterations`, `maxModelCalls`, `maxDurationMs` are in the policy but not enforced anywhere). If left unwired, mark the layers as simulation-only in the API.

### F-10 (P2) Routing LLM call is extra cost and not tracked
- **Evidence:** `router/index.ts:134-230` makes a model call with no `scanId` or `orgId`. `ox-alpha.ts:189` skips the `agent_executions` insert when those are absent, and the audit rows carry no org. `resolveRouting` is called for each agent, so each agent run costs 2 LLM calls.
- **Effect:** routing usage is invisible and cannot be budgeted or attributed to a tenant. The router's executor runs with the default model (`OX_ALPHA_MODEL`) regardless of the eligibility filter.
- **Recommendation:** pass org and scan to the routing call, or drop the LLM routing call. Choosing the top-scored candidate is already deterministic.

### F-11 (P2) Hardcoded default model
- **Evidence:** `config.ts:61` sets `OX_ALPHA_MODEL` to `meta-llama/llama-3.1-8b-instruct:free`. It is used for routing calls and for any executor call without an explicit model. Agent execution passes the routed model, so it is not hardcoded there.
- **Effect:** routing runs on a small free-tier model that may not exist in the catalog or be eligible, and the router is not constrained by the registry's eligibility rules.

### F-12 (P2) Audit and usage gaps
- **Evidence:** `ox-alpha.ts:241` audits only a success or failure summary per call chain, with `resourceId` possibly `undefined` (`scanId as unknown as string`). It records no model, token usage or attempts. `audit()` swallows DB failures. Per-attempt rows go to `agent_executions` only when scan and org are known. `recordStart` and `recordEnd` swallow all errors silently. `recordEnd` for failed attempts stores the elapsed time since the start of the whole chain, not the attempt.
- **Effect:** the audit trail is best-effort and loses data silently. Model inputs and outputs are not retained, so there is no replay.

### F-13 (P2) Output validation is lenient where it matters
- **Evidence:** `orchestrator.ts:274-322`.
  - Invalid findings (bad severity) are silently dropped. The result is still SUCCESS.
  - `finding.status` defaults to OPEN.
  - Finding `evidenceIds` are filtered against the supplied set. The earlier `hasInvalidEvidence` check fails the whole result when any id is foreign, which is strict, but a finding with no ids is kept and only fails later in quality.
  - `parsedJson` of `false` or `0` is treated as failure. Findings from the model keep the model-supplied `findingId`, which can collide with another agent's id.
  - There is no schema library: the checks are hand-written, and `confidence` defaults to 50 when missing.
- **Recommendation:** use a zod schema and fail or warn on dropped findings.

### F-14 (P3) Smaller issues
- **Simulate crash:** `routes/regeneration.ts:13` and `routes/instructions.ts:225` can throw on malformed bodies (500s). `getInstructionProfile(...)!` is dereferenced before the null check.
- **Dead code:** `persistSeoFindings` in `scan-pipeline.ts` and `adapters.ts` are unused.
- **Evidence collection:** `collectEvidence` isn't wrapped in a transaction. Its logical-key branch relies on `ON CONFLICT`. The 24h freshness rule is hardcoded.
- **Response headers:** discovery stores full response headers (`discovery.ts:154`), which could include `Set-Cookie`, and sends them to the third-party model. `redactEvidence` strips only key and value patterns.
- **Instruction versions:** the `/versions` endpoint always returns one hardcoded entry.
- **Instruction validator:** the injection filter is a keyword regex over system-generated text, not over model or user text. It protects little because planner text is controlled. The test "keeps website-content prompt injection out" only checks that the string is not in the plan.
- **Evidence lineage:** the recursive CTE has no cycle or depth guard.
- **Provider coverage:** there is a single provider (OpenRouter, credential `OPENROUTER_API_KEY`). There is no provider failover. Retries and fallback models are within OpenRouter only.

## Real versus placeholder verdicts

- **Evidence, quality, regeneration and adaptation stubs:**
  - Evidence store and validator are real and used.
  - The quality evaluator is a real weighted scorer, but its inputs are shallow (F-04) and it can ACCEPT empty results.
  - Regeneration and adaptation are real decision functions that nothing calls. They are unit-tested at 3 cases each.
- **Mock or hardcoded responses:** the simulate path returns a deterministic stub with `confidence: 0` and a warning. It is labelled `simulate: true` and no real path returns it. There is no fake success when the key is missing: the pipeline marks `unavailable`, which is correct.
- **Malformed output:** invalid JSON is retried and then fails. Valid JSON with bad shape yields a FAILED result rather than a stored value. This part is sound.

## Endpoints the frontend should consume

- **Auth:** `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/me`. Send `Authorization: Bearer` and `x-org-id` on every call, with `credentials: "include"` for the refresh cookie.
- **Core flow:** `/websites` (list, create), `/websites/:id/verify`, `/scans` (create), `/scans/:id/status`, `/scans/:id/report` or `/reports/:scanId`, `/scans/:id/findings`, `/scans/:id/cancel`.
- **Overview pages:** `/dashboard` and `/monitoring/*`.
- **Advanced or admin pages:** `/models*`, `/routing*`, `/agents*`, `/ai/*`, and the cross-domain and remediation endpoints.

**Backend gaps the frontend will hit:**
- There is no scan list endpoint. Only `/websites/:id/scans` and `/dashboard` expose scans.
- There is no organization or membership endpoint, so no org names, roles or invites.
- There is no password change or reset, and no email verification.
- There is no website delete or deactivate endpoint, even though the schema has an `active` flag.
- Nothing returns the user's role per org. `/auth/me` returns org ids only.
- `/scans/:id/events` cannot work with a native `EventSource`, because that cannot send an `Authorization` header. It must use fetch streaming.

## Findings

### P1

**F-01 [P1, BROKEN/SECURITY_GAP] Rate limiting keys on `request.ip` with no `trustProxy`.**
- Evidence: `app.ts:28-36` creates Fastify with no `trustProxy`; `app.ts:56-63` keys the limiter on `request.ip`. The app is meant to run behind App Platform (the comment at `app.ts:110`).
- Impact: behind a load balancer every client probably shares one IP. The limits would then be global: login is 10 per 15 minutes for all users, register is 5, and the general limit is 200 per minute for everyone. That means a lockout and DoS of auth. If the deployment is not proxied, `request.ip` is correct and this is fine.
- Fix: set `trustProxy` to the platform hop count, and key auth limits on IP plus normalized email. Add per-account failed-login throttling.
- Tests needed: `inject()` with `x-forwarded-for`, asserting separate buckets per client IP.

**F-02 [P1, SECURITY_GAP] `z.coerce.boolean()` treats the string `"false"` as `true`.**
- Evidence: `config.ts:29,31` for the QA flags; `config.ts:14` for `DB_SSL_REJECT_UNAUTHORIZED`.
- Impact: `validateProductionSecurityConfig` (`config-security.ts:4`) only rejects the exact string `"true"`. In production, `QA_VERIFICATION_BYPASS_ENABLED=false` plus `QA_ALLOW_PRODUCTION_BYPASS=false` passes the guard but parses to `true`/`true`. The QA bypass then becomes live for any email in `QA_AUTHORIZED_EMAILS`. The DB flag fails safe. `production-security-config.test.ts:25` asserts the unsafe pair is accepted.
- Fix: parse with an explicit enum, `z.enum(["true","false"]).transform(v => v === "true")`, and have the production guard run on the parsed config.
- Tests needed: `loadConfig({..., QA_VERIFICATION_BYPASS_ENABLED:"false"}).QA_VERIFICATION_BYPASS_ENABLED === false`.

**F-03 [P1, TENANCY_GAP] Global registries can be changed by any tenant's owner or admin.**
- Evidence: `models.ts:60,96,106` and `agents.ts:110,121` use `requireRole("owner","admin")`, which is a per-org role. The writes are global: `registry.service.ts:193,216` run `UPDATE models ... WHERE id=$1`, and `agents/registry.ts:564,584` run `UPDATE specialist_agents ... WHERE agent_type=$1`.
- Impact: registration is open and every registrant becomes owner of their own org. Anyone can therefore disable models or agents, or trigger a catalog refresh, for every tenant.
- Fix: add a platform-admin concept (an `is_platform_admin` flag or a separate allowlist) for global mutations, or make the enable/disable state per-org.
- Tests needed: a second-org owner gets 403 on `/models/:id/disable`.

**F-04 [P1, SECURITY_GAP] The SSL scanner bypasses SSRF protection and is open to DNS rebinding.**
- Evidence: `ssl.ts:19` calls `tls.connect({host: hostname, ... rejectUnauthorized:false})`. It never calls `checkUrlSafety` and does not use the pinned IP from `fetch.ts`.
- Impact: an attacker adds and verifies their own domain, then points its DNS at an internal address. The scanner connects to port 443 there. Certificate issuer, SAN, subject and expiry are persisted into findings and returned to the user, which is an internal cert disclosure and a port probe.
- Fix: run `checkUrlSafety`, connect to the pinned IP with `servername` set, enforce a timeout, and honor the URL port.
- Tests needed: with DNS mocked to a private IP, the SSL scanner must refuse.

**F-05 [P1, SECURITY_GAP] The IPv6 and IPv4-mapped check is incomplete, and it also wrongly blocks real domains.**
- Evidence: `ssrf.ts:43-52`.
  - The `::ffff:` branch calls `isPrivateIPv4` on the dotted form only. WHATWG URL and c-ares return the hex form (`::ffff:7f00:1`). **Verify** by running `new URL("http://[::ffff:127.0.0.1]").hostname`.
  - An attacker-controlled AAAA record of `::ffff:7f00:1` passes `checkUrlSafety`, and `fetch.ts:172` then pins it. The result is a dual-stack loopback or internal connection.
  - `ssrf.test.ts:145` passes only because the mocked `resolve4` throws on the IP literal, so it is right for the wrong reason.
  - The check also misses `::`, `fe80::/10` addresses starting `fe9`/`fea`/`feb`, `fec0::/10`, `ff00::/8`, `64:ff9b::/96` and `2002::/16`.
  - IPv4 documentation ranges are missing too.
- Second bug, a false positive: `ssrf.ts:47` runs `startsWith("fc") || startsWith("fd")` on the hostname itself, not only on IP literals. Hostnames such as `fcc.gov`, `fda.gov`, `fdic.gov` and `fcbarcelona.com` are rejected.
- Fix: parse IPv6 properly (for example with `node:net` `BlockList`, or an `ipaddr.js`-style normalizer) and only apply the IPv6 check to literals or resolved addresses. Block mapped, NAT64 and 6to4 forms by extracting the embedded IPv4.
- Tests needed: mocked AAAA `::ffff:7f00:1` and `::ffff:a00:1`; hostnames `fcc.gov` and `fdexample.com` must be allowed; `fec0::1` and `ff02::1` must be blocked.

**F-06 [P1, BROKEN] Crashed or deadlocked scans stay `running` forever.**
- Evidence: the worker claims only `status='queued'` (`scan.service.ts:923-931`) and flips it to `running` with no lease. Lease expiry is only consulted inside `claimScanExecution`, which is called after that claim. No sweeper requeues `running` scans with an expired lease. Shutdown (`index.ts:22-28`) waits 30 s and then calls `process.exit`.
- Related paths that strand a scan:
  - A failed `scan_modules` insert in `createScan` (`scan.service.ts:305-310`; no transaction) leaves missing rows. Later, `claimed.length===0` and `current[0]` is undefined, so the code treats it as "another worker owns this" and returns silently (`scan.service.ts:463`).
  - After a lease loss the code returns without a final status or event.
- Impact: the scan never finishes, SSE hangs, and the stuck scan occupies the tenant's concurrency slot.
- Fix: add a sweeper that requeues or fails `running` scans with `execution_lease_until < NOW()`, create the scan and its modules in one transaction, and mark scans failed on graceful-shutdown timeout.
- Tests needed: crash simulation, plus a DB integration test for the sweeper.

**F-07 [P1, BROKEN] One failed, partial or cancelled scan stops scheduled monitoring.**
- Evidence: `finalizeMonitoringRun` sets `monitoring_configs.status='FAILED'` for any non-completed scan, including a user cancel (`monitoring.service.ts:564-567`). `claimDueMonitoring` and `runMonitoringNow` both require `status='ACTIVE'` (`:381`, `:411`), and `enabled` stays true. Only `/resume` recovers it.
- Impact: the failure is silent from the UI's point of view.
- Fix: keep scheduling after a failure, or auto-recover on the next success. Do not mark FAILED for a user cancel.
- Tests needed: simulate a cancelled scan and assert the config remains schedulable.

### P2

**F-08 [P2, BROKEN] SSE endpoint problems (`scans.ts:273-349`).**
- The handler writes to `reply.raw` without `reply.hijack()`. In Fastify 5 an async handler that returns `undefined` without sending logs a "Promise may not be fulfilled with 'undefined'" error. **Verify** with an integration test. The `onSend` hooks, security headers and CORS headers are also skipped for raw writes.
- The stream ends only on `scan_completed` or `scan_failed`. `scan_failed` is emitted nowhere (grep shows only the consumer at line 328). A cancelled scan emits `scan_cancelled`, and a crashed scan emits nothing, so those streams never terminate.
- There is no heartbeat, no max duration, and no per-user or per-org connection cap. Each connection runs a DB query every 500 ms. The poll callback can overlap and swallows errors (`:339`).
- Fix: use `reply.hijack()` with CORS and security headers set manually, end the stream on terminal scan statuses, add a heartbeat and a limit.

**F-09 [P2, SECURITY_GAP] No refresh-token reuse detection.**
- Evidence: `consumeRefreshToken` (`auth.service.ts:132-169`) revokes the token and the request then fails if it is replayed, but it does not revoke the token family or the user's other tokens. Rotation is also not atomic with creating the new token: if `createRefreshToken` fails, the user is logged out.
- Related: expired tokens are never purged (a growing `refresh_tokens` table); `revokeAllUserTokens` exists but is never called; there is no password change or reset flow.

**F-10 [P2, SECURITY_GAP] Disabled users, and logout after access-token expiry.**
- `authenticate` and `requireOrgMember` never check `users.active`, so a disabled user keeps API access for up to 15 minutes. Refresh does check it.
- `POST /auth/logout` requires a valid access token. After expiry the client cannot revoke its refresh cookie.
- The JWT has no `iss`/`aud`/`alg` pinning or token-type claim. Login also hardcodes `"15m"` instead of `config.JWT_ACCESS_EXPIRES_IN`.

**F-11 [P2, SECURITY_GAP] Login enumeration and weak throttling.**
- The dummy bcrypt hash at `auth.service.ts:86` is malformed, so `bcrypt.compare` likely returns immediately, which makes timing differ between known and unknown emails (verify).
- `ACCOUNT_DISABLED` returns 403 before the password check.
- Register returns 409 `EMAIL_EXISTS`.
- Throttling is per IP only (see F-01). `register` also bcrypt-hashes before the uniqueness check, a CPU DoS vector within the 5-per-15-minute limit.
- There is no password maximum. bcrypt truncates input at 72 bytes.

**F-12 [P2, ERROR_HANDLING_GAP / info leak] Route-level catches turn arbitrary exceptions into raw 4xx responses.**
- `auth.ts:64-67`: any error (including DB connection text) becomes a 401 with `e.message`, except invalid credentials.
- `auth.ts:94-96`: refresh returns the raw message with `code` possibly undefined, and a DB blip logs the user out.
- `websites.ts:74-77` and `:112-115`: any exception becomes 422 with the raw message, for example a pg unique-violation text.
- Fix: whitelist known coded errors and rethrow everything else to the central handler.

**F-13 [P2, TENANCY_GAP, low-medium] Open registration creates unbounded orgs and nothing limits what a tenant can create.**
- No cap on websites, monitoring configs, monitoring rules, or the `alertConfig` JSON size per org.
- `POST /monitoring` has no duplicate-website check, so several configs can fan out scans for the same site.

**F-14 [P2, BROKEN, scan.service] The final scan update is not checked.**
- `scan.service.ts:678-680` updates `... AND execution_owner=$4 AND execution_lease_until > NOW()` without checking the row count. If the lease expired, the scan row keeps its old status, but the worker still finalizes monitoring, snapshots, emits `scan_completed` and audits.
- Persistence is not transactional: `persistFinding`, evidence, scores and the snapshot are separate statements.
- `finalizeMonitoringRun` is called with `.catch(() => undefined)` (`scan.service.ts:687`, `:955`; `scans.ts:266`). A failure leaves the run in `RUNNING` with no log.
- Previously persisted findings are reloaded into `allFindings` and then re-added if their module re-runs, which double-counts in scoring.

**F-15 [P2, BROKEN] Scan and monitoring fan-out failures.**
- `runMonitoringNow` inserts a `monitoring_runs` row and then calls `createScan` (`monitoring.service.ts:415-424`). `ScanAdmissionError` has no `statusCode` in this path, so the API returns 500 and leaves an orphan `RUNNING` run with a 10-minute lease.
- `processDueMonitoringJobs` (`:460-481`) calls `createScan` after the config's `next_run_at` was already advanced. An admission error aborts the loop for remaining orgs and loses that period's run.
- Expired runs are reaped only when that org still has a due config.
- The scan worker is one serial loop (`workerRunning`) shared with monitoring and notifications, so one slow scan, up to 300 s, delays everything. The per-tenant concurrency limit is moot in practice.
- A single scan can overrun its 300-second budget, because the deadline is checked only between modules and a module's fetch chain is bounded only per step.

**F-16 [P2, ERROR_HANDLING_GAP] Cancel is unguarded and unaudited.**
- `scans.ts:257` runs `UPDATE scans SET status='cancelled' WHERE id=$1` with no org and no status guard (check-then-act race). A scan that finished between the read and the write is flipped to cancelled.
- In-flight module fetches are not aborted.

**F-17 [P2, TENANCY_GAP] Admission limits are check-then-insert.**
- `enforceScanAdmission` (`scan.service.ts:274-289`) is not atomic, so concurrent requests all pass.
- `modules` is not allowlisted, and duplicate modules hit the `scan_modules` unique constraint and return 500.

**F-18 [P2, BROKEN] Monitoring snapshot key is lossy.**
- `buildSnapshot` builds the finding key as `module:category:severity:affected_urls`, without the title (`monitoring.service.ts:856`). Distinct findings with the same key collapse in the `Map`, so changes are missed.
- The evidence query (`:824-829`) scans every `finding_evidence` row for the org, not just the scan.
- The remediation proposal upsert (`cross-domain.service.ts:101`) overwrites content after approval while keeping `APPROVED`.

**F-19 [P2, SECURITY_GAP] The SSL scanner reports false criticals.**
- `ssl.ts:94-107` reports a critical "certificate could not be retrieved" for any transient connect error or timeout, and the module is marked `completed`, so it is never retried.
- Wildcard SAN matching is a loose `endsWith`, so `*.example.com` also matches `a.b.example.com`.
- It ignores the URL port and checks `url.startsWith("https://")` case-sensitively.
- `rejectUnauthorized:false` means untrusted or self-signed chains are never flagged.

### P3

- **F-20 [P3] Trailing CORS, header and redirect issues.**
  - `app.ts:131-137` registers a dead `onRequest` no-op for auth rate limits, after routes.
  - There is no `helmet`. Headers are hand-rolled, and a CSP with `style-src 'unsafe-inline'` is attached to JSON.
  - There are no explicit `bodyLimit`, `requestTimeout` or `connectionTimeout`. The CORS refinement in `config.ts:37` rejects `*` in every environment, not just production. `CORS_ORIGIN` defaults to localhost.
- **F-21 [P3] Unvalidated ids give 500 instead of 400.**
  - Non-UUID `:id` params and a non-UUID `x-org-id` hit Postgres error 22P02 and return 500 (`auth.ts:54`, most routes).
  - `monitoring` and the AI evidence/quality routes skip the uuid check.
  - Most routes use `parsed.error.message` (a JSON string) and omit `requestId`. The shape is inconsistent with `errorHandler`, so the frontend must handle both.
- **F-22 [P3] Unpaginated lists.** `/websites/:id/scans`, `/scans/:id/evidence|findings`, `/dashboard` websites and history, cross-domain and remediation, `/ai/tasks/:id/*`. Pagination exists only on websites, monitoring list, changes and alerts. `/dashboard` runs several subqueries per website.
- **F-23 [P3] Audit coverage is incomplete.**
  - No audit for scan cancel, failed website verification, monitoring rule create/update, or notification attempts without an org.
  - Login failures have no `userId`, `requestId` or IP.
  - `audit()` swallows write failures (acceptable for general events, not fail-closed for the QA bypass).
  - Audit rows also use `as unknown as string` casts.
- **F-24 [P3] Miscellaneous.**
  - `/lineage` can recurse forever on a cyclic graph.
  - `ensureRuntimeSchema` runs DDL at startup, outside the migration runner.
  - `withTransaction` can mask the original error if `ROLLBACK` fails.
  - `unhandledRejection` kills the process.
  - `agents.ts` swallows DB errors as empty lists.
  - `/auth/me` returns stale orgIds from the JWT.
  - The verification DNS name and meta token use `zignaneural`, but the QA domain and project name use `zigmaneural`. Confirm which spelling the UI instructions show.
  - `confidence` in `buildCrossDomainFinding` is a constant 75.
  - The normalized website URL drops port and query, so non-default-port sites cannot be scanned.
- **F-25 [P3] Dependencies.** Many tenant filters rely on the app role bypassing RLS. The RLS policies target the Supabase `authenticated` role, so the API (connected as an owner role) is the only enforcement point. Application-level filters are therefore the sole tenant barrier.

## Verified good

- bcryptjs with 12 rounds.
- Refresh tokens are random 48-byte values stored as SHA-256 hashes, with an atomic `UPDATE ... RETURNING` consume that blocks simple replay.
- The refresh cookie is `httpOnly`, `sameSite=strict`, path-restricted, and `secure` in production.
- CSRF risk is low because API calls use Bearer tokens.
- Redirects are re-validated and DNS-pinned in `fetch.ts`. Body size, redirect count and timeouts are enforced. Userinfo URLs are rejected. Decompression is disabled.
- All SQL is parameterized.
- The error handler returns a generic 500 and logs context.
- `requireOrgMember` does a real membership lookup per request.

### Migration-by-migration notes

- **008-010 and 012 are small but real.**
  - 008 is two quality tables.
  - 009 is four regeneration tables.
  - 010 is `adaptation_decisions`.
  - 012 is a single column (`websites.verification_environment`).
  - Their file names do not describe them ("012_qa_verification" is one `ALTER`). 008-010 create the dead tables above, so they are placeholder-level.
- **017-019:** tiny FK-cascade patches whose names do not match their content.
- **Not idempotent on re-run:**
  - 013 and 014 use bare `ADD CONSTRAINT`.
  - 015 and 016 add `UNIQUE (id, org_id)` constraints without guards.
  - 022 does guard its constraints and policies, but not its audit-log policies.

  The runner's version table is the only guard.
- **022 FKs on existing data:** the new composite FKs, for example `scans(website_id, org_id)`, will fail the whole migration if any legacy row has an inconsistent org. The risk is real but unverified.
- **Drift with `supabase_setup.sql`:** it covers only 001-011 (921 lines) and is labelled "LEGACY REFERENCE ONLY". Migrations 012-022 are absent: the extra column, the idempotency indexes, `reports`, the lease and agent-claim tables, all cross-domain and monitoring tables, and every policy. It writes `schema_migrations` rows for 001-011, so the runner would continue from 012 against such a database. Its DO-wrapped body differs from the real files.
- **Migration runner (`migrate.ts`):**
  - Good: it takes a session advisory lock, runs each migration in its own transaction, records the version after success, and rolls back on error.
  - Bad: the file list is hard-coded, so an unlisted file is silently ignored.
  - Bad: there is no checksum, so an edited, already-applied migration goes unnoticed.
  - Bad: there is no down path, and no record of the file name.
  - Risk: the session-level advisory lock is unreliable behind a transaction-mode pooler (Supabase port 6543).
  - Risk: the SSL branch requires a CA bundle if the platform CA is not trusted.
  - Neutral: production SSL is on by default; `DB_SSL_REJECT_UNAUTHORIZED` is only validated by `config-security`.
  - Neutral: `validateProductionSecurityConfig` runs before the `DATABASE_URL` check.
- **Tenant-isolation gaps:**
  - `findings`, `evidence` and `monitoring_snapshots` have an `org_id` but no policy (deny-all, which is safe but inconsistent).
  - `adaptation_decisions` has no `org_id`.
  - `routing_*` and `evidence.org_id` are nullable or have no FK.
  - `routing_decisions` has no FK on `org_id`.
  - `scans.org_id` and `findings.org_id` are NO ACTION, which is fine for deletes only because the rows go in the same statement.
  - No `FORCE ROW LEVEL SECURITY`, so the backend role, which owns the tables, bypasses RLS. App code is the only tenant guard and never sets a per-request setting.
- **RLS policy design:**
  - The frontend has no Supabase client, `SUPABASE_*` is read only in `config.ts`, and app JWTs carry no `role`, so the Data API policies are effectively dead code.
  - A `USING (true)` policy does not exist.
- **Dangerous deletes:**
  - `organizations` → `memberships` and `websites` cascade down through scans, findings, evidence, reports and monitoring. It is blocked by `audit_log.org_id`.
  - `models` cascades into `model_history`.
  - `users` deletion is blocked by `audit_log`, `websites.created_by`, `scans.triggered_by` and `instructions.created_by`.
  - `findings` are deleted by composite-FK cascade through three lineage paths (017-019).

## 3. Scripts, dependencies and deploy config

# ZigmaNeuralIntelligence functional audit: completion backlog

## Method and confidence

I split the audit across four read-only agents (frontend, backend and security, AI layer, database and docs). Their findings come from reading code. Nothing was executed: no tests, `tsc` or `pnpm audit`. I spot-checked one claim myself, F-001.

All other findings are static-analysis conclusions from the agents. Items marked "verify" need a runtime check.

Many items overlap across agents. I merged them and kept the highest severity.

---

## Executive summary

The application's skeleton is real. Authentication, website onboarding, scan queueing, monitoring, evidence storage and the model router are implemented against a real database. The frontend has no mock data.

The product does not work end to end today, for three reasons:
1. **F-001:** the evidence insert violates a `NOT NULL` column, so every scan's evidence write should fail.
2. **F-002:** no model is ever promoted to an eligible status, so every real AI run fails.
3. **F-003:** production would enable the QA bypass despite config saying `"false"`.

About 17 of 37 frontend routes are placeholders. The Monitoring page's management UI is unreachable. Settings pages show fabricated "live" data.

Several tenancy and security gaps remain. There are also no HTTP-level tests of auth, RBAC or tenancy.

---

## Findings (P0 and P1 in full; P2 and P3 in the tables below)

Each P0/P1 finding lists area, status, evidence, what is wrong, fix and tests. Dependencies and risk are folded into the fix and the execution order.

### P0

**F-001: Evidence insert violates a NOT NULL column**
- **Status:** BROKEN. I verified this statically; it is not runtime-confirmed.
- **Evidence:**
  - `db/migrations/001_initial.sql:158` defines `evidence.type VARCHAR(100) NOT NULL` with no default.
  - Migration 007 drops `NOT NULL` only on `finding_id` and adds `evidence_type`. No migration touches `type`.
  - Both inserts in `ai/evidence/store.ts:11,14` list `evidence_type` but not `type`.
  - `scan.service.ts:803` sets `type` with a later `UPDATE`, which never runs if the insert fails.
  - The only test that inserts evidence (`reliability.integration.test.ts:24`) supplies `type` explicitly, which masks the bug.
- **Effect:** every evidence write should fail, so scans and the AI pipeline break. The live database may differ from the migrations, so confirm against it.
- **Fix:** supply `type` in the inserts, or add a migration that drops `NOT NULL` on the legacy column.
- **Tests:** an integration test that goes through `collectEvidence` with no hand-supplied `type`.

**F-002: No path makes any model eligible, so real AI runs always fail**
- **Status:** BROKEN.
- **Evidence:**
  - `ai/catalog.service.ts:281` inserts new models as `DISCOVERED`.
  - `calculateEligibility` maps `DISCOVERED` to `PENDING_REVIEW`.
  - `getEligibleModels` keeps only `ELIGIBLE`.
  - `enableModel` flips `enabled` but not the status.
  - No migration seeds models.
- **Effect:** routing returns `NO_CANDIDATES`, and the orchestrator throws `MODEL_FAILURE` at `orchestrator.ts:129`. Every scan's intelligence stage ends `FAILED`.
- **Fix:** add an approve or promote workflow, seed a baseline model, and add a startup warning when the eligible pool is empty.
- **Tests:** an integration test from catalog refresh through approval to routing, against a database and a fake provider.

**F-003: QA bypass parsed wrongly, so it can be enabled in production**
- **Status:** SECURITY_GAP. Two independent agents found this.
- **Evidence:** `config.ts:29-31` uses `z.coerce.boolean()`, and `Boolean("false")` is `true`.
  - `config-security.ts:4` rejects only the raw string `"true"`.
  - `app.yaml` sets both flags to `"false"`.
  - `production-security-config.test.ts:25` asserts that this pair is accepted.
  - `app.yaml` also commits a `QA_AUTHORIZED_EMAILS` address.
- **Effect:** the QA bypass is probably live in production for that email. It lets an owner or admin mark a website verified without proof, limited to the QA domain.
- **Fix:** parse with `z.enum(["true","false"]).transform(...)`, run the production guard on the parsed config, and remove the committed email.
- **Tests:** `loadConfig` with `"false"` yields `false`, plus an inverted version of the existing test.

### P0

**F-001: Evidence insert violates a NOT NULL column**
- **Status:** BROKEN. I verified this statically; it is not runtime-confirmed.
- **Evidence:**
  - `db/migrations/001_initial.sql:158` defines `evidence.type VARCHAR(100) NOT NULL` with no default.
  - Migration 007 drops `NOT NULL` only on `finding_id` and adds `evidence_type`. No migration touches `type`.
  - Both inserts in `ai/evidence/store.ts:11,14` list `evidence_type` but not `type`.
  - `scan.service.ts:803` sets `type` with a later `UPDATE`, which never runs if the insert fails.
  - The only test that inserts evidence (`reliability.integration.test.ts:24`) supplies `type` explicitly, which masks the bug.
- **Effect:** every evidence write should fail, so scans and the AI pipeline break. The live database may differ from the migrations, so confirm against it.
- **Fix:** supply `type` in the inserts, or add a migration that drops `NOT NULL` on the legacy column.
- **Tests:** an integration test that goes through `collectEvidence` with no hand-supplied `type`.

**F-002: No path makes any model eligible, so real AI runs always fail**
- **Status:** BROKEN.
- **Evidence:**
  - `ai/catalog.service.ts:281` inserts new models as `DISCOVERED`.
  - `calculateEligibility` maps `DISCOVERED` to `PENDING_REVIEW`.
  - `getEligibleModels` keeps only `ELIGIBLE`.
  - `enableModel` flips `enabled` but not the status.
  - No migration seeds models.
- **Effect:** routing returns `NO_CANDIDATES`, and the orchestrator throws `MODEL_FAILURE` at `orchestrator.ts:129`. Every scan's intelligence stage ends `FAILED`.
- **Fix:** add an approve or promote workflow, seed a baseline model, and add a startup warning when the eligible pool is empty.
- **Tests:** an integration test from catalog refresh through approval to routing, against a database and a fake provider.

**F-003: QA bypass parsed wrongly, so it can be enabled in production**
- **Status:** SECURITY_GAP. Two independent agents found this.
- **Evidence:** `config.ts:29-31` uses `z.coerce.boolean()`, and `Boolean("false")` is `true`.
  - `config-security.ts:4` rejects only the raw string `"true"`.
  - `app.yaml` sets both flags to `"false"`.
  - `production-security-config.test.ts:25` asserts that this pair is accepted.
  - `app.yaml` also commits a `QA_AUTHORIZED_EMAILS` address.
- **Effect:** the QA bypass is probably live in production for that email. It lets an owner or admin mark a website verified without proof, limited to the QA domain.
- **Fix:** parse with `z.enum(["true","false"]).transform(...)`, run the production guard on the parsed config, and remove the committed email.
- **Tests:** `loadConfig` with `"false"` yields `false`, plus an inverted version of the existing test.

### 3. Backend endpoint status

All endpoints require auth except `/health`, `/ready`, register, login, refresh and the static SPA. They derive the org from a membership-checked `x-org-id`, so the body `orgId` is ignored. Queries are parameterized.

Roles vary: viewers can read, members can create, owners and admins can administer.

No endpoint has an HTTP-level test.

Endpoints with **no frontend consumer** (consistent across the agents; the second group sits on routes the frontend does consume under other names): `/websites/:id`, `/websites/:id/scans`, `/scans/:id/{status,evidence,report,quality}`, `/:scanId/cross-domain`, `/:scanId/remediation`, remediation approve and reject, `/ai/evidence/*`, `/ai/regeneration/*`, `/ai/quality/*`, `/models/preferences/:orgId`, `/models/eligible`, `/agents/types`, `/agents/:type/{versions,executions}`.

Also unused by the UI are `/auth/me`, `/scans/:id/{cancel,events,findings}`, `/models/catalog/status`, enable/disable model, `/routing/policy` POST, `/agents/plan`, the monitoring rules endpoints and `/monitoring/alert/:id`.

**Frontend calls with no backend route:** `GET /websites/:id/monitoring` (`apiGetMonitoringHistory`). It is unused.
